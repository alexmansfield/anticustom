# Color System Spec

Draft reference for the next iteration of the color/token system. Captures the
decisions reached so they don't get re-derived, and flags what still needs
validation before `styles/generate.php` changes. Evolves the 5-role colorway
model recorded in [ADR 0012](adr/0012-generated-tokens-with-per-value-override.md).

---

## 1. Layers of abstraction

Three tiers. **Only the first two are mandatory.**

| Tier | Name | Purpose | Example | Required? |
|------|------|---------|---------|-----------|
| 1 | **Primitive** | Raw palette + lightness ramps. No meaning. | `--neutral-dark` | Yes |
| 2 | **Semantic (colorway)** | Intent, theme-swappable. The theming seam. | `--colorway-hard-contrast` | Yes |
| 3 | **Component** | Per-component override only. | `--card-heading-color` | **Optional** |

**Tier 3 is an escape hatch, not a required pass-through.** Components reference
tier-2 tokens directly in their CSS (as `card/styles/aristotle.css` already
does). A component token is introduced *only* when that component must deviate
from the tier-2 default. This keeps the system from needing a closed,
ever-growing "component role" vocabulary (background/heading/text/button…),
which would never cover dividers, focus rings, badges, status dots, etc.

**Why tier 2 must exist:** skipping it (primitives → component roles directly)
forces every component to re-derive "what's legible on my surface" and makes a
colorway swap touch every component. The semantic layer is the single place that
flips per theme.

## 2. Tier-2 vocabulary

A colorway is expressed as an **open contrast scale + a few hued intents**, not a
fixed role list. The contrast scale is what makes it role-agnostic: any element
picks the contrast step it needs without us pre-naming the element.

### 2a. Surface + contrast scale (neutral emphasis)

Anchored to the surface. Named by **contrast (soft↔hard), not lightness
(light↔dark)** — soft/hard is relative to legibility, so the same component CSS
survives a light→dark colorway flip; "light/dark" inverts and breaks.

The **anchor token is `surface`** (not `base` — "base" is already a primitive
color name and would collide). `surface` is unambiguous and standard
(Material/Spectrum).

**Default colorway wires 4 contrast steps:**

```
surface
  ├─ ultra-soft-contrast   (barely distinct from surface — hairline borders)
  ├─ soft-contrast         (muted/disabled text, subtle fills)
  ├─ hard-contrast         (body + high-emphasis text)
  └─ ultra-hard-contrast   (headings / max legibility)
accent
```

- The **primitive ramp still carries its full set of stops** — now spanning
  literal `white` (L100) and `black` (L0) endpoints
  (`{color}-white` … `ultra-light` … `ultra-dark` … `{color}-black`); the
  *default colorway* just maps a few. A designer adds intermediate steps
  (`semi-hard-contrast`, a mid `contrast`, etc.) by overriding — they're not
  generated by default. White/black endpoints still yield *tinted* hovers — see
  §3d.
- **No default middle step.** Components that previously leaned on a mid
  `contrast` slot (e.g. body text) remap to `hard-contrast`. Worth a sweep when
  implementing.
- **All step names are editable** — these are sane-default keys, not fixed
  identifiers (see §2d).

### 2b. Hued intents

- `accent` — brand highlight / primary action.
- `success` / `warning` / `danger` / `info` — meaning-bearing.
- Contrast alone cannot express hue intent ("this is a *danger* badge"), so these
  are separate from the contrast scale.
- **Statuses inherit from the default colorway** and are *not* re-specified per
  colorway, unless a colorway is doing a genuine light/dark inversion. Keeps each
  colorway definition tiny.

### 2c. Foreground pairing (`-on`)

**Every fill-capable slot carries a paired foreground.** A fill with an
illegible label is broken *at rest*, so the pairing must exist regardless of
hover — Material's `on-` model (`primary`/`on-primary`).

- `accent` → `accent-on`, each status → `{status}-on`, `surface`'s foreground is
  the contrast scale itself.
- **Auto-derived** per colorway by luminance: `-on` = whichever of {near-white,
  near-black} (or `surface` vs `ultra-hard-contrast`) has the higher contrast
  ratio against the fill. Because the pick is against *that colorway's* fill, it
  comes out right per colorway with zero hand-authoring.
- **Overridable** via explicit `{slot}-on` (same hybrid pattern as ADR 0012).

A minimal colorway definition therefore is roughly:
`{ surface, soft→family, hard→family, accent→family }` + "inherit statuses",
with `-on` colors and the full ramp expanded by the generator.

### 2d. Generation rules (names + sparseness)

- **All token names are editable.** Contrast steps, intents, and `surface` are
  *default keys* in config, not fixed identifiers. The generator emits whatever
  keys exist; renaming is a data edit. This requires the generator to iterate the
  config lists rather than a hardcoded slot array (today
  `$colorwayTokens = ['base','hard-contrast',…]` is hardcoded — that must become
  data-driven; see §7).
- **Sparse generation — unset tokens do not exist.** If a colorway doesn't
  define a slot, the generator emits nothing for it. No blank/placeholder tokens.
- **Contract: components must always carry a `var()` fallback**, because any
  token may be absent. `color: var(--colorway-hard-contrast, #0f172a)`. An unset
  token with no fallback = no color. This is already the pattern in
  `card/styles/aristotle.css`; sparse generation makes it mandatory, not
  optional.

## 3. State derivation (hover / active)

Two axes, kept separate:
- **WHERE** the state is computed (which layer).
- **HOW** the shift direction/magnitude is chosen.

### 3a. Plain surfaces — primitive-level, band-derived (default)

Hover/active is a property of a swatch's lightness, **not** of the role it plays.
Compute once per primitive color (`--neutral-dark-hover`), scheme-independent;
colorways **inherit by reference** (`colorway_derive_state` already aliases
`--colorway-hard-contrast-hover` → `--neutral-dark-hover`, no recomputation).
Used by surfaces, borders, dividers — anything without a text-contrast
constraint. This is the existing `color_interaction_shifts` band logic and it is
correct for this case.

### 3b. Interactive fills that carry text — pair-aware, interface-level

A button's binding constraint is **fill↔label contrast**, not fill↔surface. The
label is a tier-2 token (`accent-on`), so hover for a fill must be computed at
the **colorway/interface layer** where the pair is known — *not* at the
primitive layer. The pair resolves locally within the `[data-colorway]` block.

The rule is **not** "always shift away from the label" — that breaks at the
extremes (you can't make near-black blacker). The constraint flips by regime:

| Fill position | Binding constraint | Hover direction |
|---|---|---|
| Near an extreme (most solid buttons) | **Visibility** (huge contrast headroom) | Toward center / toward label — spend the headroom |
| Mid-tone | **Legibility** | Away from the label |

**Unified rule:** *shift into available room — toward center at the extremes,
away from the label in the mid-range — floored at the contrast minimum.*

Note: the existing band logic **already handles the extremes correctly**
(near-white → darken, near-black → lighten = "toward center"), so it never
produces "blacker black." The only change needed is making the **mid-band
(L25–75) direction label-aware** and applying the contrast floor. This is a
targeted patch to one function, not a rewrite.

### 3c. Overrides

Keep the explicit `{slot}-{state}` override hatch — intent occasionally beats
math (a brand may insist "primary always darkens on hover"). Already supported.

### 3d. Achromatic endpoints (white / black) — derive tints at generation time

Every primitive ramp ends in **literal `white` (L100) and `black` (L0)**, so an
element can be genuinely `#fff` / `#000` at rest — *not* near-white/near-black.
Their hover states, however, can and should be **tinted**.

Pure white/black are achromatic **in appearance** in every color model (HSL,
OKLCH, RGB): at max/min lightness, chroma is necessarily zero, so a hue cannot be
*seen*. But the ramp's **source hue is not lost** — the generator builds each
ramp forward from the source color and holds the hue throughout. So it emits a
literal endpoint **and** a tinted state derived from the retained hue:

```css
--primary-white: #ffffff;                /* renders white */
--primary-white-hover: <tint at L~92>;   /* tinted — generator still holds hue 220 */
--neutral-white-hover: <gray at L~92>;   /* achromatic source → gray hover */
```

A white button on a hued ramp hovers to a tinted off-white; on the neutral ramp
it hovers to gray. Pure white at rest, correct tint on hover, no near-white
endpoint anywhere.

**Why generation time, not runtime:** CSS Color 4 makes HSL/OKLCH hue and
saturation **powerless at L=0/100** — `hsl(from white h s calc(l - 8%))` snaps to
gray, because white reports no usable hue. Reading the hue back *out of* the white
value at runtime fails. The generator never hits this: it works *forward* from the
source hue, so the tint survives the extreme. (If runtime derivation is ever
needed, store the hue in a sidecar token — `--primary-h` / `--primary-s` — and
compose from that, rather than clawing it back from `#fff`.)

Generate ramps in **OKLCH** (replacing the current HSL `color_shade`) for
perceptually even steps and no hue drift. Independent of the white/black
decision, but it makes the near-endpoint tints noticeably cleaner.

## 4. Testable invariants

State derivation produces two checkable guarantees per generated colorway
(fits the testable-failure-states / layout-invariant harness direction,
ADR 0004):

1. **Legibility:** for every fill, `contrast(fill, fill-on) ≥ 4.5:1`
   (`≥ 3:1` for large/bold) at **rest, hover, and active**.
2. **Visibility:** for every interactive fill, `ΔL(rest, hover)` ≥ a perceptible
   minimum — so a fill pinned against the 0/100 wall never produces a dead hover.

The "blacker black" failure is invariant (2) failing; the "hover ate my text"
failure is invariant (1) failing. Both are deterministic and harness-checkable.

## 5. Open questions / to validate before coding

- **Mid-tone "toward edge" direction** in the current band logic: for mid-tone
  *colored fills on a light surface* this can *reduce* surface contrast. Validate
  against a real button on a real surface before trusting it.
- **Band-boundary discontinuity** (L≈25/50/75): two near-identical mid-tones can
  hover in opposite directions. Usually invisible at small shifts; confirm it's
  acceptable.
- **Contrast-floor clamp vs flip:** in the mid-tone tight case, decide whether to
  clamp the magnitude or flip direction when the floor would be breached.
- **Variable count:** 4 directions × 6 shades × (base/hover/active) ≈ 72 vars
  per colorway. Fine for a few hand-authored colorways; gate ramp generation
  (or emit fewer steps) before auto-generating a colorway per enabled color, or
  `tokens.css` balloons.
- **`-on` derivation target:** decide the two candidate poles for auto-pick —
  literal `white`/`black`, or `surface`/`ultra-hard-contrast`.
- **OKLCH migration:** moving `color_shade`/`hsl_to_hex` from HSL to OKLCH is a
  generator change with its own validation (gamut handling, output format).
  Sequence it as its own step, not bundled with the vocabulary changes.

## 6. Summary of decisions

1. Three tiers; tiers 1–2 mandatory, tier 3 (component) optional/override-only.
2. Tier 2 = open **contrast scale** (soft↔hard) + `accent` + statuses. Anchor
   token is **`surface`** (not `base`). Default colorway wires **4 steps**
   (`ultra-soft` / `soft` / `hard` / `ultra-hard`); more added by override.
3. **All token names are editable** (sane-default keys, data-driven). Generation
   is **sparse** — unset tokens don't exist; components must carry `var()`
   fallbacks.
4. Every fill-capable slot has an auto-derived, overridable `-on` foreground.
5. Statuses inherit from default unless doing light/dark inversion.
6. State derivation: **surface-anchored** (primitive-level, band, default) vs
   **label-anchored** (interface-level, pair-aware) for interactive fills.
7. Label-anchored rule = "into available room — toward center at extremes, away
   from label mid-range — floored at 4.5:1." Existing band logic already correct
   at extremes; only the mid-band needs to become label-aware.
8. Two testable invariants: legibility (≥4.5:1 across states) and visibility
   (perceptible ΔL).
9. Ramps span **literal `white`/`black` endpoints**; tinted hovers are derived at
   **generation time** from the retained source hue (runtime recovery fails —
   hue is "powerless" at L=0/100). Generate ramps in **OKLCH**, not HSL.

## 7. Extensibility

A designer can extend the system — more contrast levels, an extra intent beyond
`accent` — through three points, ordered least → most invasive.

### 7a. Data-driven (no code) — the main path

Both "more contrast levels" and "extra intent" should be **edits to
`defaults.json`, not code**.

- **More contrast levels** → add a stop to the `hues` ramp (e.g. `semi-contrast`
  at L50). The generator already iterates `$hues`, so it emits
  `--colorway-{newstep}` + `-hover`/`-active` automatically. Additive and
  non-breaking — existing components reference their existing steps; new ones opt
  in. This is the payoff of an *open* scale over a fixed role list.
- **Extra intent beyond `accent`** → add a color with `enabled: true` and
  register it in the intents list. It auto-gets a ramp + states at the primitive
  tier (already happens) and, at tier 2, `--colorway-{intent}` + an auto-derived
  `--colorway-{intent}-on` pair + states. The `-on` luminance pick works for any
  new color, so the designer never hand-specifies the label color.

**Required enabling change:** the colorway slot enumeration must be
**data-driven**. Today `generate.php` has
`$colorwayTokens = ['base','hard-contrast','contrast','soft-contrast','accent']`
hardcoded — the *ramp* is data-driven but the *slot list* is not. Making intents
a config list and deriving contrast steps from the ramp is what turns "extend the
system" from a code change into a data edit.

### 7b. Per-component (CSS only)

New tokens are plain CSS variables, so any component can reference a new contrast
step or intent in its style file with no schema change. Additive, non-breaking.

### 7c. Escape hatch (always available)

For a genuinely one-off color that *shouldn't* enter the shared vocabulary (a
marketing gradient, a single bespoke badge), the `class` prop and tier-3
component tokens are the out — a designer is never forced to fork the system or
pollute the shared scale for a single use.

### Limits

- **Variable count compounds.** Each new contrast step multiplies across every
  intent × state, and vice versa. Sparse generation (§2d) plus gating (§5)
  matters *more* as the system grows, not less.
- **Naming insertion.** Inserting a level *between* `soft` and `semi-soft` forces
  a naming decision. Because all names are editable (§2d), this is the designer's
  call; ordering for soft↔hard semantics is computed by lightness-relative-to-
  surface, so the generator stays correct regardless of the chosen name.
- **Novel math needs code.** Adding levels/intents is pure data, but a *new
  derivation rule* (a new way to compute a state) is generator code — the one
  thing extension can't do as data alone.
