# Rich text is a graduated, schema-driven field type edited in the sidebar

Components opt fields into rich text via a new `richtext` field type whose options declare *capabilities*, never tiers: `marks` (bold/italic), `styles` (named styled spans), `multiline` (`<br>`), and — designed but deferred — `blocks`/`links`. The editor, toolbar, and sanitizer all derive what they permit from the same field options, so a field's schema is simultaneously its editor configuration and its security boundary. Editing happens in the explorer's sidebar component panel; the preview stays a render-only surface. Nothing off the shelf offered this (Sanity's Portable Text is the closest concept, but lives inside Sanity Studio), so the system is first-party.

## Decisions

- **Tiers are derived, not declared.** A `richtext` field with no options is tier 1 (plain text); adding `marks` yields tier 2, `styles` tier 3, `blocks`/`links` tier 4. The sanitizer supports tier 4 today; the engine and toolbar defer it.
- **Storage is sanitized HTML strings, enforced on output.** Props hold fragments like `Hello <strong>world</strong>`. `anti_rich()` (components/render.php) sanitizes on every render via `anti_rt_sanitize()` (richtext/sanitize.php), a DOM-walking allowlist derived from the field's options — so tampered stored values and interpolated `{field}` values are both neutralized at render time. `{field}` interpolation runs before output and keeps working unchanged. Only `richtext` props may contain markup; `text` stays fully escaped.
- **Named styles are a global registry with per-field opt-in.** `richtext/styles.json` maps a style name to a label and token-backed CSS declarations; each style compiles to exactly one class (`.anti-rt-<name>`), emitted by `styles/generate.php` so explorer and production share it. Component schemas select styles by name — mirroring the token philosophy (ADR 0012): global definitions, local selection. Editors pick "Highlight"; they never see a class.
- **The editing surface is a dual-view sidebar field, rendered view by default.** In the component panel, a `richtext` field renders as a WYSIWYG contenteditable driven by the engine — real marks and styled spans, Enter gated by the schema's `multiline` — with a per-field toggle to a raw-HTML textarea for direct source editing. Toggling raw → rendered re-normalizes through the engine, so hand-typed markup gets the same allowlist treatment as pasted content. Styled spans render with their real token CSS inside the field (the explorer inlines the token stylesheet page-wide).
- **Chrome is a field-anchored, selection-triggered bubble.** The toolbar core is mount-agnostic (`richtext/toolbar.js`): it turns an editor's features into buttons and dispatches commands; a *mount* (`{show, hide, destroy}`) decides presentation. The shipped mount is a bubble that appears while a selection exists in a richtext field, pinned to the field's top edge — it does not chase the selection. A collapsed caret inside a named-style run shows a reduced bubble instead: a single chip that removes the entire contiguous run (the Ghost/Tiptap link pattern). The scoping rule: marks (bold/italic) are per-character paint and stay strictly selection-scoped; named styles are one-per-range entities, so a bare caret — which states no scope — may only remove, with the engine inferring the run as the scope. Applying a style always requires an explicit selection, and an explicit selection is never silently enlarged. Attached-row and inline-preview mounts are possible later implementations of the same contract.
- **The engine is hand-rolled on a segment model, with a swap line.** `richtext/engine.js` (window.AntiRT) parses a region into a flat array of characters carrying `{bold, italic, style}`, transforms that model, and re-renders canonical DOM — normalization is a property of rendering, not a pass. `beforeinput` gating means disallowed operations never reach the DOM. Undo is a per-editor snapshot stack. The `AntiRT.createEditor` surface is the escape hatch: a ProseMirror/Tiptap adapter could replace the internals without touching schemas, sanitizer, or chrome.
- **Preview sync uses the standard sidebar path.** Widget changes write the HTML string into props and debounce-re-render the preview like every other field; the preview is never an editing surface, so no caret-preservation machinery exists.

## Considered Options
- **Inline preview editing (built, then removed)** — a first iteration attached `contenteditable` to the rendered preview itself, Ghost-style, via request-scoped edit mode (`anti_edit_mode()`), per-field region attributes (`data-anti-field` emitted by an `anti_rich_attrs()` helper through the templates' latent `$editable` slot), and a selection-following bubble. It worked, but sidebar editing was the intended interaction, and maintaining two editing surfaces for the same prop wasn't worth it; the server-side edit-mode machinery was removed rather than kept dormant. A future inline mode (e.g. antisloth front-end editing) can cite this convention — the deliberation lives in the grill thread above.
- **Tiptap/ProseMirror engine** — battle-tested editing model, but an ESM package graph is foreign to this build-free PHP repo, and its document model sits between schemas and HTML. Kept as the documented swap path.
- **Structured JSON storage (portable-text style)** — safer in principle and renderer-agnostic, but requires a PHP renderer and breaks free interpolation over plain string props.
- **Raw-HTML textarea in the sidebar** — zero work, but editors hand-write tags, which is exactly what the graduated system exists to avoid. Survives as the toggle view.
- **Per-component style definitions** — more local, but styles compile to CSS that must ship globally; per-component definitions would let "Highlight" drift between components.

## Consequences
`intro` and `card` fields demonstrate tiers 1–3. Deferred, by design: tier 4 blocks/links in engine and toolbar; a richer treatment of child-slot fields (hero's intro title is edited as JSON). Accepted costs: a colorway-dependent named style may look different inside the panel than on the canvas (the panel's colorway context differs); undo history is per-field and per-session.
