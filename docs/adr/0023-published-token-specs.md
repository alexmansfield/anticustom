# Token guarantees are published specs: the spec defines tokens, the site provides values

A **spec** is a named, versioned, immutable artifact defining the guaranteed token set — token names and their emitted CSS variables (`spacing.m` → `--space-m`), never values — existing independently of any skin. Skins *follow* a spec; a site is **built to spec** when every spec-defined token resolves and **out of spec** otherwise; a project binds at most one spec outbound (its own promise) while installed skins bring inbound specs that are *checked, never bound*. This matches industry ontology deliberately: the layer is what Material calls system tokens and the W3C DTCG calls alias tokens — named, meaning-bearing tokens whose values live elsewhere — so the item needs no invented noun. **The spec's items are tokens.** A user's entire ontology stays one word, with adjectives doing the work: *defined by the spec*, *custom*, *missing*.

A site following a spec **contains** the spec's tokens as editor rows: non-deletable while the spec is followed (deletion attempts surface "defined by the ⟨name⟩ spec — removing it takes your site out of spec," offering the customize path), each carrying a site-owned value and a freely editable display **label** that defaults to the token's spec name — relabeling ("Gutter" for `m`) touches nothing downstream, ever, because the variable is the spec's, not the label's. A lean site satisfies a wide spec by **aliasing** — one spec token pointing at another (`xxl` uses `xl`'s value) — plain token aliasing as every design-token tool has it, replacing any separate mapping/slot apparatus. **Custom tokens** are project vocabulary beyond the spec: freely created, renamed (their slug is their variable), and deleted; skins may reference them only via chained fallback (ADR 0017), so their absence elsewhere degrades to defaults. The shipped **base spec** defines: five spacing tokens (`xs s m l xl` — the observed consumption surface; factory `xxs`/`xxl` become custom tokens), text `s m l`, six heading tokens (`--heading-1`–`-6`, resolved from the headings group's rank order per the #40 model), the pick-one bare aliases (`--border`, `--radius`, `--shadow` — named size options are never spec tokens; ADR 0021's open sets stay open), and the palette surface per ADRs 0015/0016 unchanged — palette keys and intents were this system's first spec tokens avant la lettre. `defaults.json` ships as the base spec's reference implementation, so the factory state is built to spec before the user touches anything.

The lifecycle is **draft → publish → evolve**. A draft is the freely editable token surface — add, remove, rename — seeded blank (greenfield), from the base spec, or by *starting from* any imported spec (a copy; the original's fate stays separate). Nothing is promised to anyone while drafting; in-use advisories still report consequences for installed skins. **Publishing** freezes a version; published specs are never edited by anyone — immutability, not permissions, is what makes them trustworthy (who on a team may draft or publish is host-side policy, out of scope). Evolution reopens a draft seeded from a published version and publishes the next; prior versions keep their promises to whatever follows them. At publish time the extension check runs mechanically: every token of the seed retained → stamped **extends** it, and skins following the seed are guaranteed under the successor. Going out of spec is never a hard break: consumption is `var()` with chained fallbacks throughout, so an unmet skin degrades to defaults — the promise is lost, not the rendering. The editor speaks consequences at its own abstraction ("this size is used by your site's styles — removing it means those fall back to the default"), never artifact nouns; CSS variable names appear only behind a show-token-names toggle, off by default.

## Considered Options
- **"Contract" + "mint"** — precise in-discussion, wrong in the world: "breaking the contract" reads as legal threat, "minting tokens" is unrecoverably crypto-flavored.
- **"Standard" + "guarantees"/"slots"/"roles" + mapping** — a two-population ontology (abstract slots, project tokens mapped onto them) that no user could be told in one sentence: nobody has heard of a guarantee named `space.m`, and "9 guarantees backed by 5 tokens" reads as a contradiction where "the spec defines 9 tokens; your site is missing 4" states the same fact plainly. Industry precedent (Material system tokens, DTCG alias tokens) shows the semantic tier is just called tokens; the slot/mapping machinery collapsed into spec-token rows plus ordinary aliasing with no loss.
- **Names as the guarantee, freely deletable** — re-couples names to guarantees so renaming becomes breaking; the spec-token row with a free label keeps renaming harmless while the variable stays promised.
- **Label-slug alias emission** (`--space-gutter: var(--space-m)`) — doubles the emitted surface (the #39 concern), gives every value two names, and turns relabeling into a consequence-bearing act.
- **Skins own their required names, no independent artifact** — couples the guarantee to each skin's lifecycle and forbids the goal: many skins sharing one surface.
- **Editable-in-place specs** — the promise evaporates on first edit; version-and-publish is the only honest mutation.
- **Seven spacing tokens in the base spec** — `xxs`–`xxl` is an inheritance, not a design; shipped CSS consumes `xs`–`l`, so five cover the observed surface and the extremes remain custom tokens.

## Consequences
The generator emits spec-token variables from spec + site data (family aliases and heading rank variables become spec-backed rather than convention-backed). A spec is a file: the base spec ships in `styles/`, a project stores which spec it follows, and published specs are distributable alongside the skins that follow them. The editor gains: spec tokens as undeletable rows with the out-of-spec/customize flow, aliasing, the missing-token state, the show-token-names toggle, and in-use advisories worded as consequences. #40's group model gets a rework pass against spec semantics (heading variables from rank order; scale-family CONTEXT language amended there). #39 (variable-count gating) gains a natural boundary: the promised surface is enumerable from the spec.

## Amendment (2026-08-01): the token→variable mapping is key-identity

[ADR 0027](0027-spec-owned-naming-identity-emission.md) sharpens the `spacing.m → --space-m` example above. The emitted variable is the **key verbatim** (`--{key}`); the generator applies **no** family prefix. Any namespace a spec wants (the `space-` in `--space-m`) is **embedded in the key** the spec author typed — `space-m` emits `--space-m`, `h1` emits `--h1` — chosen so every emitted variable is globally unique. This makes the layering literal: naming (key, label, emitted variable) is *entirely* spec data, and anticustom is agnostic about all three. The **label** is an independent spec-owned display string that may differ from the key; what this ADR forbids is *the engine* manufacturing a label, not a spec choosing one. A **duplicate key** — two tokens emitting the same variable — is a hard error (a broken spec). The current `generate.php` prefix hardcoding is pre-spec implementation debt, to be removed when emission reads from spec data. Everything else here stands.
