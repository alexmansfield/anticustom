# `-on` foregrounds are authored data; legibility is verify-warned, not generated

An intent's `-on` foreground is an ordinary optional palette key, hand-authored like any other slot — there is no auto-derivation. This amends ADR 0016's "auto-derived by luminance pick" clause: the default palette ships `-on` values in `defaults.json`, other palettes inherit them through the CSS cascade, and defining the key is the override (the presence-of-key idiom of ADRs 0015/0019). The spec §5 open question — which two poles the luminance pick chooses between — dissolves rather than resolves: there is no machine pick to choose candidates for, and the artboard-7 auto-pick acceptance example is retired with it.

The WCAG contrast matrix (per the recovered-precursor research, `docs/research/php-contrast-matrix.md`) backs **verification, not generation**. Verify resolves each palette's effective pairs exactly as the cascade would and emits **advisory warnings** (ADR 0007's advisory tier) below 4.5:1. Coverage is palette-level only: (1) `surface` against each **text-bearing contrast step** — an explicit config list, defaulting to `hard-contrast` and `ultra-hard-contrast`; the soft side of the scale is deliberately sub-legible (borders, dividers, subtle fills) and exempt; (2) each intent plus `accent` against its resolved `-on`, at rest and at the fill's derived hover/active (the `-on` stays fixed while the fill shifts); (3) a custom slot is checked only when an `-on` sibling key exists — the partner key is the signal that a slot is a fill. Nothing is checked at the ramp/color tier (a raw ramp has no pairing semantics); per-component checking is an editor concern, out of scope here.

Shipped defaults go soft. The four status source hexes darken to approximately their current L20 shades (the ramp is unaffected — `shade()` takes only hue/saturation from the source), and the default palette pairs a pale tint fill with the source color as text: `success: var(--success-ultra-light)`, `success-on: var(--success)` — 7.4–9.9:1 across all four statuses, quiet enough for message panels and badges alike. `accent` keeps the solid treatment (`#336699` + white, 6.0:1). The factory state is warning-free at 4.5:1; exact hexes are implementation-time tuning.

## Considered Options
- **Auto-pick between literal `white`/`black`** — one candidate always clears 4.5:1 by construction, but WCAG 2 math paints black on most saturated mid hues (white fails against all four current status hexes: 1.9–3.8:1), fighting both convention and the soft-status direction; the picked value also lands outside any palette vocabulary.
- **Auto-pick between the palette poles (`surface`/`ultra-hard-contrast`)** — stays inside the palette but in *neutral* vocabulary: a status label has no reason to draw from the gray scale when its hue owns a full ramp; and both poles can fail against a fill, so a failure policy is needed anyway.
- **Auto-pick from the status's own ramp** — the right vocabulary, but still a hidden derivation layer whose output must be overridable, explainable in the editor, and reasoned about on drift; authored data plus a warning achieves the same legibility with none of the machinery.
- **Hard error instead of warning** — treats a sub-4.5:1 pair as invalid data, but legibility floors are context-dependent (3:1 passes for large/bold text); advisory fits the two-tier model of ADR 0007.
- **Solid saturated fills + white labels as shipped defaults** — the conventional badge look; fails WCAG against every current status hue and makes statuses shout; ruled out in favor of tint-fill/dark-text, with solid looks remaining a two-key palette edit (a dark source carries white trivially).

## Consequences
ADR 0016 is amended (the auto-derivation clause only — two-token intents, `data-intent` binding, cascade inheritance, and the deleted semantic colorways all stand). Spec §2c is rewritten, §5's poles question closed, and §4's legibility invariant is enforced as verify warnings over authored pairs. Verify gains the contrast-matrix functions and the explicit text-steps list; the generator gains nothing. The `defaults.json` changes (dark status sources, tint/text intent pairs) are implementation work, sequenced by the handoff ticket. A future editor "suggest a legible value" affordance may reuse the matrix; nothing depends on it.
